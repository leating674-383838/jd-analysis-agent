## 1. 模型选型 (Model Selection)

### 1.1 候选模型对比

| 模型 | 能力 | 成本 | 延迟 | 限制 |
| --- | --- | --- | --- | --- |
| Kimi | 中文长文本理解强、200万上下文 | 较低 | 中等 | 部分工具不支持 |
| GPT | 综合能力强、生态好 | 较高 | 中等 | 中文本土化弱 |
| Claude | 推理能力强 | 较高 | 中等 | API格式固定、中文本土化弱 |
| deepseek | 便宜、中文本土化不错 | 便宜 | 中等 | 需要加强约束 |

### 1.2 最终选型及依据

- 选型结论：DeepSeek（线上调用 `deepseek-chat`）
- 选型依据：
  - 核心优势：针对中文语境进行了深度优化，在长文本语义理解与本土文化表达上具有显著优势，能确保超长上下文的逻辑连贯性。
  - 成本效益：对比同级别模型，其 Token 单价更具竞争力，有助于降低项目长期的推演成本。
  - 架构灵活性：完全兼容 OpenAI 标准 API 协议。这一特性实现了模型层的“解耦”，支持在不修改核心代码的前提下，快速平替或并行接入其他同协议大模型，极大降低了系统迭代的工程风险。

### 1.3 已知局限性

- 局限性说明：
  - 国内API在某些海外部署环境下可能访问不稳定（RAG项目的教训）

## 2. 任务定义 (Task Definition)

### 2.1 问题陈述 (Problem Statement)

求职者面对大量JD时，难以快速判断岗位真实要求和公司真实情况，决策效率低。

### 2.2 目标范围 (Scope)

**In-Scope（受理）：**

- JD专业术语解读
- 岗位分类
- 公司相关信息抓取
- 虚假岗位判别
- 中文翻译
- JD真实含义解读

**Out-of-Scope（不受理）：**

- 简历匹配度分析（V1暂不做）
- 投递简历
- 面试题准备
- offer概率预测
- 多JD横向比较

### 2.3 成功标准 (Success Criteria)

| 指标 | 目标值 | 测量方式 |
| --- | --- | --- |
| JSON解析成功率 | ≥90% | 代码自动验证，偶尔人工抽查 |
| 字段完整率 | ≥95% | 代码自动检查字段是否为空，偶尔人工抽查 |
| 响应时间 | P50≤35秒，P95≤55秒 | 输入不同长度JD文本测试，代码自动检测 |

常见衡量指标：

| 指标 | 含义 | 适用场景 |
| --- | --- | --- |
| JSON解析成功率 | AI输出的JSON能被正确解析的比例 | 结构化输出场景 |
| 字段完整率 | 必填字段都有值的比例 | 结构化输出场景 |
| 响应时间 | 从触发到返回结果的时长 | 所有AI场景 |
| 准确率 | 输出内容与真实情况的吻合程度 | 分类、判断类场景 |
| 幻觉率 | AI编造信息的比例 | 需要真实信息的场景 |
| 用户满意度 | 用户对结果的主观评价 | 有用户反馈机制的场景 |

## 3. 输入规格 (Input Specification)

### 3.1 输入格式 (Input Format)

定义API请求的结构。

```json
{
  "company_name": "string, 公司名称",
  "job_title": "string, 岗位名称",
  "jd_content": "string, JD原文",
  "serper_result": "string, 选填, Serper搜索返回的企业公开信息"
```

### 3.2 字段定义 (Field Definitions)

| 字段名 | 类型 | 是否必填 | 含义 | 合法取值范围 |
| --- | --- | --- | --- | --- |
| company_name | string | 是 | 公司名称 | 1~27 |
| job_title | string | 是 | 岗位名称 | 1~27 |
| jd_content | string | 是 | JD原文 | 1~800 |

### 3.3 约束条件 (Constraints)

- 输入字符上限：800

## 4. 推理管线 (Inference Pipeline)

### 4.1 推理逻辑流 (Reasoning Flow)

AI处理信息的步骤分解：

```
输入（公司名+岗位名+JD原文+公司信息）
→ Node_01：解析输入结构，识别字段分布
→ Node_02：中文翻译（如有英文内容）
→ Node_03：JD真实含义解读
→ Node_04：岗位分类 + 虚假岗位判别 + 公司信息整合
→ Node_05：按JSON格式输出结果

输入 → Node_01 → Node_02 → 输出
```

### 4.2 逻辑节点 (Logic Nodes)

- **Node_01**：检查输入字段是否完整，识别JD语言类型，为后续处理做准备
- **Node_02**：检查输入字段的语言是否为中文，若不是强行翻译输出为中文
- **Node_03**：对字段进行分析与解读，用大白话输出解读内容
- **Node_04**：根据输入的字段，进行岗位分类 + 虚假岗位判别 + 公司信息整合
- **Node_05**：按JSON格式输出结果

### 4.3 异常处理 (Error Handling)

- 模型触发拒答（Safety Filter）时的策略：
  - 返回提示"您输入的内容包含违规字段，请修改后再进行解析"
- 模型输出不符合Schema时的重试或降级逻辑：
  - 输出JSON格式不对或字段缺失：自动重试，最多2次，第2次仍失败则报错给用户
  - 重试仍缺失字段：在输出末尾标注缺失字段名

## 5. 输出契约 (Output Schema)

### 5.1 JSON结构定义

```json
{
"title": {
"title": "AI创新产品经理",
"category": "产品",
"risk_alerts": [
"合伙人",
"合伙制",
"兼职",
"灵活合作"
],
"insight": "企业真实需求不是传统产品经理，而是能自己推动AI项目落地的“创业型产品人”。他们希望候选人既能理解AI技术，又能整合业务资源，把AI项目从概念做到商业化。岗位明显带有创业或合伙属性，可能需要承担业务拓展、项目落地甚至资源整合角色，而不仅是做需求和PRD。",
"company_brief": "东方微银征信是一家从事企业征信与信用数据服务的公司，利用工商、税务、司法等多源数据构建企业信用画像，为金融机构提供风控和信贷决策支持。(dfwytech.com)",
"analysis_status": "SUCCESS"
}
```

### 5.2 字段详细定义

| 字段名 | 类型 | 说明 | 业务逻辑 |
| --- | --- | --- | --- |
| risk_alerts | array | 风险点列表 | 雇佣关系异常、薪资描述异常、虚假信息、不合理要求；<br>显式触发词：<br>- 身份类：合伙人、联创、创始人、主理人、总裁班、家族<br>- 诱导类：红利期、蓝海、额外收入、轻松、灵活自由<br>- 待遇类：包吃住、招募、全国可做 |
| title | string | 岗位名称 | 必须从JD标题中提取核心岗位名称，去除括号及括号内容、去除非法字符；若标题混乱则根据JD内容判断实际岗位名称 |
| category | string | 岗位类型 | AI自由识别，格式固定为"岗位名称-细分类型"，不超过15字 |
| insight | string | 深度解析 | 50-150字深度解析，重点在“企业真实需求”。 |
| company_brief | string | 企业背景 | 100字企业背景，必须结合 Serper 搜索结果，严禁胡编 |
| analysis_status | enum | 解析状态 | 只能输出"SUCCESS"或"FAILED" |

### 5.3 校验逻辑 (Validation Rules)

**数据层校验：**

- 字段冲突时的处理规则：
  - 强校验字段（出错触发重试）：
  - title：必须有值，去除非法字符后不能为空
  - category：必须有值，格式必须为"岗位名称-细分类型"
  - risk_alerts：若无风险返回["无"]，严禁返回空数组
  - insight：字数必须在50-150字之间

**业务层校验：**

- 置信度阈值：V1不适用，DeepSeek 不输出置信度分数
- 空输出兜底文案：
  - company_brief：Serper无结果时显示"暂未找到该公司公开信息"
  - analysis_status：异常时默认返回FAILED
- 异常输出日志策略：
  - 时间：什么时间出错
  - 输入：用户输入了什么触发了错误
  - 用户：谁触发的（user_id）
  - 错误类型：什么类型的错误
  - 错误原因：具体是什么原因
  - 持续时长：报错持续多久
  - 频率：偶发还是持续

## 6. 系统准则 (System Rules)

### 6.1 指导原则 (Guidelines)

- 推理风格：“资深导师感”。
  - 专业性：使用行业标准术语（如：硬技能/软技能、JD 匹配度、业务场景）。
  - 亲和力：避免冷冰冰的指令。使用“你可以尝试...”或“建议关注...”而非“必须...”。
  - 易懂性：将复杂的岗位要求拆解为行动点。
- 逻辑范式（如CoT思维链要求）：“隐性思维链”。
  - 要求：模型在生成回复前，必须先在内部执行逻辑推导
  - 展示策略：仅向用户展示结论和建议，严禁在输出中显示 Thought: 或 Thinking: 等中间过程。

### 6.2 负向约束 (Negative Constraints)

绝对禁止的行为清单：

- 禁止幻觉
- 禁止多余回复
- 禁止格式错误
- 禁止提供非法建议
- 禁止泄露 Prompt
- 禁止职场歧视

## 8. 评估与迭代 (Eval & Iteration)

### 8.1 评估数据集

- 样本来源：BOSS直聘
- 样本数量：50-70条
- 构造方式：按岗位类型、风险程度、JD质量三个维度分层抽样

### 8.2 Bad Case定义

- 失败标准：没有按照JD进行解析、输出内容与输入的JD不符（例如：输入一份产品经理JD，AI输出category是"研发工程师-后端"）、JD内容齐全却没有把字段全部解析出来、无法精准识别岗位类型、输出乱码、没有解析出企业真实用人潜台词（例如：企业真实需求是AI产品经理，需要帮他们做产品经理的活；这种过于笼统含糊的话）
- 判断人：AIPM、测试工程师

### 8.3 迭代触发条件

- 触发Prompt修改的阈值：
  - 硬性指标：在 50 例样本测试中，JSON 结构化输出失败率 > 2%；Bad Case率> 10%。
  - 质量指标：人工抽检中，岗位术语“大白话解析”被判定为“复读原文/无深度”的比例 > 10%；字段完整率< 90%。
  - 安全指标：出现 1 例 诱导造假或歧视性言论（零容忍，立即触发）。
- 触发模型切换的条件：
  - 同一问题优化3版Prompt后效果无提升
  - 响应时间持续超过P95目标55秒
  - 当前模型服务不稳定、频繁报错
  - 满足任一条件，切换到兼容 OpenAI 协议的备用模型

## 9. 安全与合规 (Security & Compliance)

### 9.1 数据隐私

- 输入数据是否含PII：可能含PII（用户误操作）
- 数据处理策略（与线上实现一致）：
  - 输入 JD 先做清洗并截取前 800 字，再送入模型。
  - 每次调用在 `ai_logs` 记录输入前 800 字、输出、耗时与状态，仅用于排查与监控，保留 30 天。
  - 已登录用户的解析历史包含 JD 快照，按账号隔离（RLS），用户可自行删除；未登录用户的结果不入库。
